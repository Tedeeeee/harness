# Codex 위임

이 스킬은 개인 규칙이다. 작업 중인 프로젝트의 규칙(진입 문서, 단계, 승인, 스킬, 커밋)이 항상 우선한다. 이 스킬은 그 흐름 안에서 **누가 무엇을 하는지**만 더한다.

## 역할

| 판단 | 예 | 누가 |
|---|---|---|
| 제품 판단 | 동작·범위·예외 정책, API 응답 모양, 데이터 구조, 화면 문구 | 개발자 |
| 설계 판단 | 계층·파일 위치, 이름, 스킬 해석, 테스트 범위 | Claude |
| 실행 판단 | 승인된 계획 안에서 코드를 어떻게 쓸지 | Codex |

- 개발자는 Claude하고만 대화한다. Codex의 의견과 질문은 Claude를 거쳐 개발자에게 간다. 개발자가 Codex에 직접 답했다고 알려 오면 그 결정을 계획에 적는다.
- **Claude**: 기획·구현 계획, 작업 나누기와 지시서, Codex 질문 처리, 검토·검증, 합치기, 프로젝트 문서 갱신, 커밋안.
- **Codex**: 의견(읽기 전용), 승인된 계획의 구현과 단위 테스트, 막히면 질문. 커밋·push·데이터베이스·운영 환경 접근은 하지 않는다.

Codex는 판단을 서둘러 내리는 경향이 있지만 의미 있는 지적도 자주 한다. 그래서 판단은 맡기지 않고, 다른 시각이 필요한 자리에서 의견을 묻는다.

## 이번 작업에 쓸지 정하기

1. **개발자 말이 먼저다.** 정해진 문장이 아니라 뜻으로 알아듣고, 애매할 때만 확인한다.

   | 개발자 말 | 뜻 |
   |---|---|
   | "혼자 해", "Codex 없이" | 의견도 구현도 Codex를 쓰지 않는다 |
   | "의견만 물어봐" | 의견만 묻고 구현은 Claude가 한다 |
   | "Codex한테 맡겨" | 구현을 Codex에게 맡긴다 |
   | "Codex한테도 물어봐" | 아래 기준과 상관없이 의견을 묻는다 |

   말한 범위는 그 작업이 끝날 때까지다. "오늘은 계속"처럼 넓히면 따른다. 새 작업은 다시 기본 기준으로 판단한다.
2. **기본 기준.**
   - 한두 파일짜리 수정, 원인 조사, 새 구조를 처음 정하는 일은 Claude가 직접 한다. 지시서를 쓰는 비용이 더 크다.
   - 계획이 구체적이고 파일 범위가 정해진 여러 파일 작업(계층 옮기기, 비슷한 패턴 반복, 테스트 작성·이전)은 구현을 맡길 수 있다.
3. **먼저 밝힌다.** 기능 작업을 시작할 때 "이번엔 Codex에게 ○○를 물을/맡길 계획"을 응답 본문에 한 줄로 쓴다. 개발자가 그 자리에서 끌 수 있게 한다. 프로젝트가 정한 응답 형식은 바꾸지 않는다.
4. 진행 중에 "혼자 해"가 오면 돌던 Codex를 멈추고, 그때까지 바뀐 것을 검토한 뒤 Claude가 이어서 한다.

## Codex에게 의견을 물을지

기본은 묻지 않는다. 다음 순서로 판단한다.

1. 결과가 **사실**(조사·분석·현황)이면 묻지 않는다. 사실은 다른 모델의 의견이 아니라 근거(문서·데이터·코드)로 확인한다.
2. **결정**이고, 틀렸을 때 되돌리기 어려우면(구조, API 계약, 데이터 구조, 운영 영향) 묻는다.
3. 쉬운 결정이어도 Claude가 확신하지 못하면 묻는다.

분석으로 시작한 요청도 기능 작업으로 넘어가는 순간부터 이 기준을 적용한다. Codex에게 구현을 맡길 때의 계획 검토·지시서 점검은 이 판단과 상관없이 항상 한다.

## 흐름

프로젝트의 단계·승인 규칙을 그대로 따르고, 각 단계에 아래를 더한다. ★는 개발자 확인이다.

1. **기획**: Claude가 현재 동작을 조사한다. 큰 판단이 걸려 있으면 같은 시점에 Codex 의견을 받는다(결론 숨김, [opinion.md](references/opinion.md)). 지적을 코드로 확인해 진짜만 추리고, 선택지·권장안과 함께 보인다. ★동작·범위·예외 확정.
2. **구현 계획**: Claude가 파일·계층·이름·스킬·테스트·계약을 정하고, 작업을 나눠 지시서를 쓴다([brief.md](references/brief.md)). Codex에게 계획 검토와 지시서 점검을 받는다. 정하지 않은 제품 판단이 드러나면 계획 승인에 섞지 않고 기획으로 돌아간다. Codex 지적으로 바뀐 점을 표시해 보인다. ★승인.
3. **구현**: Orca 작업자로 Codex를 띄운다([orca.md](references/orca.md)). 질문은 Claude가 받는다. 설계 판단이면 답하고, 제품 판단이면 맥락·선택지를 붙여 개발자에게 묻는다(★가끔). 범위가 바뀌는 질문이면 그 작업을 멈추고 기획으로 돌아간다.
4. **검증**: Claude가 검토하고, 테스트를 직접 다시 돌리고, 합친다([review.md](references/review.md)). 프로젝트 문서를 갱신하고 보고한다. ★결과 확인.
5. **커밋**: 프로젝트의 커밋 규칙을 따른다. 작업 주체(Claude·Codex)는 적지 않는다.

## 조율자 위치

- Codex에게 **구현**을 맡기는 조율은 Orca 안에서 실행 중인 Claude(채팅 탭 또는 터미널)만 할 수 있다. 환경 변수 `ORCA_TERMINAL_HANDLE`이 없으면 Orca 밖이다.
- Orca 밖에서는 의견 받기([codex-cli.md](references/codex-cli.md))만 한다. 구현을 맡겨야 하면 Orca 채팅 탭에서 이어 가자고 개발자에게 알린다.

## 지킬 것

- 프로젝트 규칙과 충돌하면 프로젝트 규칙을 따르고 충돌을 알린다.
- Codex의 보고는 확인할 대상이다. 바뀐 파일과 테스트 결과는 Claude가 직접 확인한다.
- 공유 자원을 쓰는 테스트(같은 테스트 데이터베이스 등)는 동시에 돌리지 않는다. 그런 테스트는 Claude가 하나씩 돌린다.
- 개발 서버를 띄워야 하면(화면 확인 등) 먼저 개발자에게 묻고, 개발자가 쓰는 포트와 겹치지 않게 한다.
- Codex 의견은 자료다. Claude가 코드로 다시 판단해 진짜 놓친 것만 반영하고, 버린 것도 이유와 함께 보고한다.
