# 검토와 합치기

## 검토 (작업마다)

1. 작업자 worktree에서 실제로 바뀐 파일을 본다: `git -C <worktree> status --short`, `git -C <worktree> diff`.
2. 보고한 파일 목록과 실제가 같은지, 지시서의 「고쳐도 되는 파일」 안인지 본다.
3. 프로젝트 스킬의 필수·금지 규칙을 지켰는지 본다.
4. 계획에 없던 판단이 들어갔는지 본다. 지시서에 없는 분기, 예외 처리, 응답 필드, 문구가 신호다. Codex의 약점이 드러나는 자리다.
5. 테스트는 Claude가 그 worktree에서 다시 돌린다. 보고된 결과를 그대로 쓰지 않는다.

문제가 있으면 이렇게 한다.

- 판단이 틀렸거나 범위를 벗어났으면 이유를 붙여 같은 작업자에게 되돌린다([orca.md](orca.md) 5). 맥락이 이어진다.
- 몇 줄이면 Claude가 직접 고친다.
- 제품 판단이 섞였으면 개발자에게 묻는다.

## 합치기 — 커밋 없이 작업 폴더로

검토를 통과한 변경은 커밋하지 않은 채 개발자의 작업 폴더(조율자가 있는 폴더)로 가져온다. 개발자는 평소처럼 diff를 보고, 커밋은 프로젝트 규칙대로 한다.

1. 작업 폴더 상태를 본다(`git status --short`). 다른 변경이 있으면 겹치는 파일이 없는지 확인하고, 겹치면 개발자에게 묻는다.
2. 작업자 worktree에서 변경을 패치로 만든다. 새 파일도 들어간다.

   ```bash
   git -C <worktree> add -A
   git -C <worktree> diff --cached --binary > "<임시 폴더>/<작업>.patch"
   ```

   `add -A`는 작업자 worktree의 index만 바꾼다. 커밋하지 않는다.
3. 작업 폴더에 적용한다. 먼저 확인하고 적용한다.

   ```bash
   git apply --check "<임시 폴더>/<작업>.patch"
   git apply "<임시 폴더>/<작업>.patch"
   ```

4. 작업이 여럿이면 하나씩 적용하고, 다 합친 상태에서 영향받는 테스트를 돌린다. 공유 자원을 쓰는 테스트는 하나씩 돌린다.

## 정리

- 합친 뒤 남은 작업자를 `worker-release`로 정리한다.
- 작업자 worktree는 개발자가 합친 결과를 확인한 뒤 지운다: `orca worktree rm --worktree <selector> --json`. 브랜치까지 지울지는 개발자에게 묻는다.
- 보고에 맡긴 작업, 받은 질문, 되돌린 내역을 적는다.
