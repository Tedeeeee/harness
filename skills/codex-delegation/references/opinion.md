# 의견 받기

Codex에게서 받는 것은 결정이 아니라 다른 시각이다. 실행 방법은 [codex-cli.md](codex-cli.md)를 따른다.

## 질문 양식

### 기획 — 결론을 숨긴다

Claude의 결론과 권장안을 보여 주지 않는다. 보여 주면 Codex는 대개 동의하고 끝나고, 반대로 Claude가 Codex 의견에 끌려갈 수도 있다. 둘이 갈리는 지점이 가장 쓸모 있는 신호다.

```
너는 의견만 낸다. 파일을 고치지 않는다.

## 배경
<기능 요청과 확인한 사실, 관련 파일 경로>

## 선택지
1. <선택지 A>
2. <선택지 B>

## 해 줄 것
- 선택지마다 무엇이 깨지는지, 놓친 예외 상황이 무엇인지 코드 근거(파일·줄)와 함께 찾아라.
- 하나를 고른다면 근거 코드 위치와 함께 적어라.
- 확신이 없으면 확신이 없다고 적어라.
```

"뭘 할까"보다 "무엇이 깨지나"를 묻는다. Codex의 강점(코드를 빨리 읽고 사실을 확인)은 살리고 약점(서두른 판단)은 피한다.

### 구현 계획 — 계획을 보여 주고 틀린 것을 묻는다

계획 자체가 검토 대상이므로 숨기지 않는다. 계획 검토와 지시서 점검은 한 번에 묻는다.

```
너는 의견만 낸다. 파일을 고치지 않는다.

## 승인 전 구현 계획
<계획>

## 이 계획으로 줄 구현 지시서
<지시서 초안>

## 해 줄 것
- 계획에서 빠진 파일·호출처·테스트, 프로젝트 규칙(스킬) 위반을 코드 근거와 함께 찾아라.
- 이 지시서만 보고 혼자 구현한다면 짐작해야 하는 곳을 모두 적어라.
```

## 지적 처리

Claude가 지적마다 코드로 다시 확인하고 넷으로 나눈다.

| 분류 | 처리 |
|---|---|
| 놓친 것 | 코드로 확인되면 반영한다 |
| 이미 고려한 것 | 그대로 둔다 |
| 틀린 것 | 코드 근거를 들어 버린다 |
| 제품 판단을 바꾸자는 것 | Claude가 혼자 받거나 버리지 않고 개발자에게 질문으로 가져간다 |

버릴 때도 반영할 때처럼 근거를 댄다. Claude는 자기 계획을 지키려고 지적을 가볍게 넘기는 쪽으로 쏠릴 수 있다.

## 보고 양식

의견을 받았을 때만 응답 본문에 적는다. 출처를 구분하고, 버린 지적도 한 줄 이유와 함께 적어 개발자가 뒤집을 수 있게 한다.

```
Codex 검토 N건
- 반영: <지적> — <확인한 근거>
- 이미 반영: <지적> — <계획의 어느 부분>
- 반영 안 함: <지적> — <이유>. 원하면 다시 본다.
- 질문: <제품 판단을 바꾸자는 지적> — <선택지>
```
